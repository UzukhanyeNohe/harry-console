01 ANALYSIS

What you're actually building — the read.

All 5,585 lines of v1.5 reviewed — every model tag, installer, CLI flag and provider-behaviour claim verified against live sources. The architecture is sound, achievable on 16 GB, and now executable: hand it to the agents and the repo governs itself. Eight decisions carry the whole project — protect them.

The North Star — new in v1.3

"Harry is a trusted personal AI teammate who grows more useful with the user while remaining transparent, permissioned, private by default, and under the user's control."

Every architectural decision gets tested against five questions — and if a feature fails one, it waits:

1More useful in daily life?
2User clearly in control?

01

The laptop is the control plane, not the brain

Your best insight. The Pavilion never needs to run a frontier model. It runs identity, memory, policy and routing — and rents frontier intelligence from Claude and OpenAI only when a task earns it. This single idea makes the whole project practical.

02

Capability router, not provider router

Scoring every task on privacy, difficulty, coding, vision, cost and latency — then routing — means Harry survives any provider changing, dying, or being replaced. No vendor lock-in at the core.

03

Security enforced in code, not prompts

Permission tiers, approval gates, audit logs and injection defense that don't rely on a model behaving. A malicious email saying "ignore your rules" hits a policy engine, not a personality. Rarer than it should be.

04

Subscription-first: the money problem, solved structurally

v1.2's biggest upgrade. Harry's cloud escalation runs through the tools your subscriptions already include — Codex CLI and Claude Code, orchestrated as command-line workers with structured JSON output. No API billing on day one, no scraping, no borrowed tokens. Direct APIs stay defined in models.yaml but switched off until they're actually worth paying for.

05

The Experience Compiler — Harry gets smarter without retraining

Every cloud consultation is recorded, reflected on, and — when a workflow stabilizes — compiled into a tested local skill that runs free and offline next time. A seven-level maturity ladder (L0→L6) governs promotion. This is system-level learning: cheaper, inspectable and reversible, where fine-tuning would be none of those.

06

Phase gates kill demo-driven development

"The demo worked once" never advances a phase. Each has measurable exit criteria — proven Git rollback, injection tests passing, restore drills that actually run. This is what makes Harry reliable instead of a weekend toy.

07

The human layer: identity, consent, and scoped authority

v1.3's contribution. Harry opens with a first-run conversation, keeps personality as editable config, and asks before remembering. On the power side, approvals can become scoped grants — but an always-confirm list (money, credentials, deploys) never auto-approves, elevation is temporary, and one stop command halts everything. A personality with a permission slip.

08

The repo outlives the chats

v1.4's law. Project memory lives in repo-owned files — CURRENT_STATE, PROJECT_MEMORY, HANDOFF, REVIEW_LOG — never in any provider's chat history. The recovery requirement makes it an invariant: delete every Codex conversation, every Claude conversation, even swap the primary model, and a competent new agent resumes the project accurately from the repository alone.

⛨PERMISSION MEMORY

Approvals that learn — inside hard limits

request → capability → risk: low runs · medium asks once · high always asks · admin = temporary elevation, then the process exits

12 THE BRAIN — CANONICAL VS VISUALIZER

Harry owns the brain. The graph tool only gets a photograph.

v1.5's whole addition is one refusal: no note-taking app ever becomes Harry's memory. Logseq, Obsidian, Joplin, SiYuan, a vector-DB vendor — none of them. Harry keeps canonical memory and hands a viewer a one-way, privacy-filtered, disposable projection. Delete the projection and Harry loses nothing.

canonical brain → privacy filter → projection builder → generated graph → viewer renders it  ·  ONE WAY, ALWAYS

The hard invariant — everything else is downstream of this

A visualization tool may display Harry's knowledge, but it must never become the source of truth for it. Harry must keep working if the viewer is missing, broken, uninstalled, or changes its storage format. No core capability may import a visualizer as a runtime dependency.

Which makes the decision not "Harry uses Logseq" but "Harry supports visualizer adapters — Logseq is adapter #1." That distinction is what keeps a beta third-party database out of your memory's critical path.

Canonical vs derived — the layout that enforces it

Runtime personal memory lives outside the Git repo. The repo's docs/agent-context/ files are engineering memory for the agents building Harry — a different thing entirely, and conflating them is how brains get committed to GitHub.

%USERPROFILE%\HarryData\ ├─ brain\ ← CANONICAL. brain.sqlite, knowledge\, indexes\ ├─ derived\ ← DISPOSABLE. visualizers\logseq\ ├─ backups\ └─ logs\

Harry owns memory IDs, timestamps, provenance, privacy class, relationship edges, retention state and verification state. A visualizer owns none of those concepts — it receives a rendering of them.

The projection privacy firewall

Not every memory belongs in a graph UI. Everything crosses a policy boundary before a viewer sees it, and the projected text may be rewritten into a safe summary — the same sanitisation Career Mode already does.

Hand-edit a generated page. Harry's memory is unchanged; the next rebuild overwrites the edit.
Secret exclusion
Seed fake keys, passwords, .env content and an employer-confidential item. None may appear in any profile.
Offline
Pull the network. The projected graph is still browsable.
Reproducibility
Same snapshot + same policy → identical nodes, edges, IDs and privacy decisions.
Failure domain
Corrupt the projection. Harry says "the visualization needs rebuilding" — never "my memory is corrupted."

Research · what changed after v1.5 was written

v1.5's caution about the storage transition was correct — and the situation has since resolved into something more actionable. Logseq has split into two products. The DB version shipped its 2.0 beta in July 2026 with SQLite as the canonical store; the file-based Markdown app continues as Logseq OG in its own repository, and the project states OG stays maintained and that no one is forced to migrate. Both remain AGPL-3.0. The DB README still warns plainly that data loss is possible and recommends automated backups.

Two findings sharpen the isolation policy rather than soften it. First, the DB version now ships an optional MCP server that can run against the current graph from either the desktop app or the CLI, with create, edit and search capability — so §46.1's "no MCP for Harry's graph" is no longer a precaution about a hypothetical, it is a real shipping surface that must be verified off. Second, the DB plugin API is itself still in beta, which is a second reason the "zero plugins" starting position is right.

Field notes — seven tweaks before you hand 3B to Codex

1 · The firewall is written as a blocklist. Make it an allowlist. §45.1 enumerates what to exclude, but §55 asks Claude to verify filtering is deny-safe. Those are different systems. A blocklist fails open on every memory type invented after it was written. Project only when privacy_class is explicitly in the profile's include list — then add the test that proves it: introduce an unclassified memory type and assert it does not appear.

2 · Classification won't catch a key pasted into a note body. Category filtering protects categories; it does nothing about an API key sitting in the middle of an otherwise-projectable decision note. Add entropy/regex scanning as an independent second layer at projection time, fail closed, and log the redaction. Extend the seeded-secret test to secrets inside allowed memories.

3 · Target Logseq OG for adapter #1. File graphs are exactly the shape this design wants — generated, diffable, human-inspectable, trivially deletable, and reproducible enough to make the checksum and reproducibility gates almost free. The DB version inverts that: SQLite becomes canonical, files stop being hand-editable, and it is beta with an explicit data-loss warning. Wrong shape for a disposable mirror. Treat DB graphs as a later, separate adapter, and never import one.

4 · Consider promoting StaticGraphVisualizer to adapter #0. Your requirement is read-only, disposable, on-demand graph exploration that works offline and on the projector. A generated self-contained HTML graph delivers all of it with no third-party runtime in a privacy-critical path — no Electron, no plugin surface, no MCP server, no sync toggles anyone has to remember to disable, no beta migration, and effectively zero idle RAM on a 16 GB machine. It also renders on the projector and the phone PWA you already shipped. Logseq then becomes the power-user view it deserves to be, rather than the default dependency.

5 · Build to a temp directory and swap atomically. Generate into logseq.tmp, then rename over the live path, so a half-written projection can never be opened and browsed as if it were complete. Mark generated files read-only while you're there — it won't stop a determined edit, but it turns the edit-the-mirror mistake into a deliberate act rather than an accident.

6 · Make the manifest a receipt. PROJECTION_MANIFEST.json should carry the canonical snapshot hash, the profile ID and policy version, per-type included/excluded counts, the redaction count and the generator version. That turns the reproducibility gate from a judgement call into an assertion, and gives brain.projection.audit something real to check.

7 · Assert egress; don't just toggle a firewall rule. Strict-offline mode should end with a test that zero outbound connections occurred during a viewer session, not merely that a rule was added. Worth knowing: a Windows Firewall rule keyed to an executable path stops applying when an Electron app updates into a new path — so revalidate the rule, or the mode fails silently open. Also wire brain.visualizer.* into the emergency stop, so "Harry, stop everything" closes an open projection.

Where this ends up

Logseq is an acceleration tool, not the end state. A future Harry-native brain UI reads the same Brain Projection API and can add what no note app will give you — memory provenance, privacy class, confidence, filters by mode, and "why do you remember this?" with a delete button next to it. When that lands it simply becomes the default view. No migration is required, because the visualizer never owned the data. That is the whole point of building it this way now.
